# Elastic Detection Engineering and Threat Hunting

## Overview

Elastic Security was used as the primary SIEM and detection platform for the APT29 Living-off-the-Land adversary-emulation project.

The detection strategy focused on behavioral indicators rather than relying only on malware signatures or known malicious file hashes.

Because the simulated APT29 activity made extensive use of legitimate Windows utilities such as PowerShell, `mshta.exe`, WMI, scheduled tasks, WinRM, and Registry Run keys, the detection rules were designed around:

* Process relationships
* Command-line activity
* PowerShell Script Block Logging
* Windows authentication events
* Registry modifications
* WMI events
* Network connections
* Active Directory replication events

A total of **16 MITRE ATT&CK-mapped detection rules** were engineered and validated in Elastic Security.

---

# Detection Engineering Methodology

Detection rules were developed incrementally rather than creating all rules first and testing them only after the complete attack chain was finished.

The validation workflow was:

```text
CALDERA Ability
      |
      v
Execute Technique
      |
      v
Generate Endpoint Telemetry
      |
      v
Search Event in Kibana
      |
      v
Create / Tune Detection Rule
      |
      v
Execute Technique Again
      |
      v
Confirm Elastic Alert
```

For each ATT&CK technique:

1. The corresponding CALDERA ability was executed.
2. Generated telemetry was located in Kibana.
3. Relevant fields were identified.
4. A KQL or EQL rule was created.
5. The ability was executed again.
6. The Elastic Security Alerts view was checked.
7. False positives were analyzed.
8. The query was tuned when necessary.
9. The rule was re-tested before being accepted.

This validate-before-progressing approach reduced the chance of discovering broken rules only during the final attack-chain run.

---

# Telemetry Sources

The primary telemetry sources used by the detection rules were:

| Telemetry                 | Purpose                                 |
| ------------------------- | --------------------------------------- |
| Sysmon Event ID 1         | Process creation                        |
| Sysmon Event ID 3         | Network connections                     |
| Sysmon Event ID 13        | Registry modifications                  |
| Sysmon Event IDs 19/20/21 | WMI persistence                         |
| PowerShell Event ID 4104  | Script Block Logging                    |
| Security Event ID 4624    | Successful logon                        |
| Security Event ID 4662    | Active Directory object access / DCSync |
| Elastic Agent             | Endpoint log forwarding                 |
| Fleet                     | Centralized agent management            |

PowerShell Script Block Logging was especially important because it provided visibility into decoded PowerShell commands even when encoded or obfuscated PowerShell was executed.

---

# Detection Rule Configuration

All sixteen rules were configured using:

```text
Execution interval: 1 minute
Look-back window: 5 minutes
```

The rules used either KQL or EQL depending on whether the detection required a simple event match or correlation between multiple events.

# Detection Rule Catalogue

## 1. Phishing via HTA and Mshta Proxy Execution

**MITRE ATT&CK**

```text
T1566.001
T1218.005
T1059.001
```

**Risk Score:** 99

### Detection Logic

```kql
event.code: "1" and
process.name: "powershell.exe" and
process.parent.name: "mshta.exe"
```

This rule identifies PowerShell launched by `mshta.exe`, which was generated by the custom HTA spearphishing simulation.

---

## 2. Obfuscated PowerShell Execution

**MITRE ATT&CK**

```text
T1059.001
T1027
```

**Risk Score:** 73

### Detection Logic

```kql
event.code: "1" and
(process.name: "powershell.exe" or process.command_line: *powershell*) and
(
    process.command_line: *-EncodedCommand* or
    process.command_line: *-enc* or
    process.command_line: *-e * or
    process.command_line: *frombase64string* or
    process.command_line: *-nop* or
    process.command_line: *-bypass* or
    process.command_line: *-windowstyle hidden* or
    process.command_line: *-w hidden* or
    process.command_line: *invoke-expression*
)
```

This rule identifies PowerShell commands containing common execution-evasion or obfuscation indicators.

## 3. Suspicious PowerShell Script Block Content

**MITRE ATT&CK**

```text
T1059.001
T1546.003
T1021.006
```

**Risk Score:** 73

### Detection Logic

```kql
event.code: "4104" and
(
    powershell.file.script_block_text: *Invoke-Command* or
    powershell.file.script_block_text: *New-CimInstance* or
    powershell.file.script_block_text: *lsadump* or
    powershell.file.script_block_text: *ConvertTo-SecureString* or
    powershell.file.script_block_text: *Register-ScheduledTask* or
    powershell.file.script_block_text: *Net.Sockets.TcpClient*
)
```

A key lesson during development was that the correct Elastic field was:

```text
powershell.file.script_block_text
```

rather than:

```text
winlog.event_data.ScriptBlockText
```

Using the wrong field would cause the detection to miss the attack activity.

# Detection Tuning

False-positive analysis was performed throughout rule validation.

Examples of normal activity that required tuning included:

* Software updates executing from temporary directories
* Legitimate Registry Run-key modifications
* Machine-account authentication
* Anonymous network logons
* Benign PowerShell path-management commands

Three rules required additional changes after the final validation run:

```text
System and AD Discovery
- Added parent-process conditions.

Scheduled Task Persistence
- Added Register-ScheduledTask detection.

Data Exfiltration Over C2
- Added destination port 9999.
```

The purpose of tuning was to improve detection precision without losing visibility into attack behavior.

# Threat Hunting

After the final attack-chain execution, six manual threat hunts were performed using Kibana Discover.

The goal was to determine whether an analyst could reconstruct the attack from raw telemetry without relying exclusively on automated alerts.

---

# Hunt H1 - CALDERA Child Processes

### Objective

Identify processes launched by the CALDERA Sandcat agent.

The Sandcat agent was staged as:

```text
C:\Users\Public\splunkd.exe
```

### KQL Query

```kql
event.code: "1" and
process.parent.name: "splunkd.exe"
```

### Investigation Value

This query identifies child processes generated by the CALDERA agent and provides a useful pivot for reconstructing the attack timeline.

# Threat-Hunting Results

The six threat hunts connected isolated endpoint, persistence, identity, and network events into a coherent attack timeline.

Hunt H1 was particularly useful because the CALDERA Sandcat agent provided a common parent-process pivot.

The hunting process demonstrated that the attack could be reconstructed independently from the automated Elastic Security alert feed.
